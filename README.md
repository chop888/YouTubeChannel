# YouTubeChannel
# 自動化ロードマップ

## 自動化に着手する順番（結論）

台本生成 → 音声合成 → 動画組み立て → リサーチ → 投稿・分析 の順で自動化する。

理由：台本生成が最もAI向きの工程であり、他の全工程（音声・編集・投稿）の起点になるため。
リサーチも重要だが、台本フォーマットが固まってから自動化した方が「何を集めるべきか」が明確になる。

## 工程別 自動化整理表

| 工程 | 自動化のしやすさ | 自動化すべきタイミング | 想定ツール・方法 |
|---|---|---|---|
| 台本生成 | 高 | フェーズ1（最初に着手） | Claude API（プロンプトテンプレ化） |
| 台本の事実確認 | 低〜中（自動チェックは補助程度） | 継続的に人が担当 | Claude APIによるダブルチェック＋人の最終確認 |
| 音声合成 | 高 | フェーズ2 | VOICEVOX／CeVIO等のAPI |
| 立ち絵イラスト素材 | 中（初回作成は人力、以降は使い回し） | 最初に1〜2パターン作成すれば以降は不要 | 自作 or 外注、AI画像生成の活用 |
| YMM4タイムライン組み立て | 中〜高（スクリプト開発が必要） | フェーズ3 | .ymmpファイル（JSON的構造）を操作する自動生成スクリプト |
| **テーマ・企画案の自動生成** | **高** | **フェーズ3.5（テンプレ確定後、リサーチ本格化の前）** | **Claude API（コンセプト＋テンプレ＋既存ネタを渡して生成）＋スプレッドシート自動追記** |
| 競合・ネタリサーチ | 中（一次収集は容易、企画判断は人の目が有効） | フェーズ4（台本フォーマット確定後） | YouTube Data API＋Claude API（Web検索併用） |
| サムネイル・タイトル案 | 中（たたき台は自動化できるが最終判断は人推奨） | フェーズ5以降 | Claudeで複数案生成＋AI画像生成＋人による最終選定 |
| 投稿（予約投稿） | 高 | フェーズ5 | YouTube Data API |
| 再生数・維持率の分析 | 高 | フェーズ5 | YouTube Data API（定期取得） |
| 次のネタ選定へのフィードバック | 中（収集は自動化できるが採用判断は人推奨） | フェーズ5以降、継続的に運用 | 分析結果をスプレッドシートに蓄積→人が確認 |

## フェーズ別ロードマップ

### フェーズ1：台本生成の自動化
- 台本テンプレ（比較型／おすすめ〇選型）をプロンプト化する
- Claude APIに「テーマ名」を渡すだけで台本が出力される状態を作る
- キャラ2人の掛け合い形式では、話者ごとにセリフを振り分けるプロンプト設計がカギ
- 最初の数本は人が目を通してプロンプトを調整する

### フェーズ2：音声合成の自動化
- 台本テキストをVOICEVOX等のAPIに渡し、キャラごとの音声ファイルを自動生成
- 感情パラメータ（抑揚等）の調整もこの段階で仕組み化する

### フェーズ3：動画組み立ての自動化
- 音声ファイルの長さを基準に、立ち絵の切り替え・テロップ・画像挿入タイミングを自動配置するスクリプトを開発
- YMM4のプロジェクトファイル（.ymmp）を直接生成／編集する

### フェーズ3.5：テーマ・企画案の自動生成
- コンセプト・台本テンプレ・既存ネタストックを渡し、Claude APIで新規テーマ案を週次生成
- 生成結果はスプレッドシートの「台本ネタストック」シートに自動追記
- 生成頻度は週1回、1回あたり3〜5件を目安にする（過剰生成による消化不良を防ぐ）

### フェーズ4：リサーチの自動化
- YouTube Data APIで競合チャンネルの新着動画・再生数・登録者数を定期取得
- Claude APIで「気づき・差別化ポイント」「台本ネタ候補」を生成し、スプレッドシートに自動追記

### フェーズ5：投稿・分析・フィードバックの自動化
- YouTube Data APIで予約投稿
- 再生数・維持率の定期取得
- 伸びているネタの傾向を、次の台本ネタ選定にフィードバックする仕組み化

### フェーズ6：全体スケジューリング
- cron または GitHub Actions で、フェーズ1〜5を定期実行するジョブとして統合
- 例：週1回「ネタ選定→台本→音声→動画組み立て」を自動実行し、人は最終確認と投稿判断のみ行う

## 完全自動化しない方がよい部分（人の関与を残す）

- 台本の事実確認（誤情報のリスク回避）
- 最終的な動画の質チェック（誤読・違和感のあるテンポ）
- サムネイル・タイトルの最終選定（CTRに直結するため）
- 企画・ネタの採用判断（データは自動収集でよいが、選ぶのは人が担当）
- 著作権・素材のライセンス確認

## 「裏で24時間Claude Codeを動かす」場面について

Claude Codeは基本的に**対話的なターミナルツール**なので、それ自体が「24時間常駐して待ち構える」動き方はしません。常時稼働のイメージが生まれるのは、こういうケースです。

**① 定期実行(cron/スケジューラ)**
「1日1本、テーマを決めて台本→音声→タイムライン組み立てまで自動生成する」といったジョブを、`claude -p`(ヘッドレスモード)でcronから毎日決まった時刻に叩く形。これが最も現実的な「自動チャンネル運用」の形で、常時プロセスが立ちっぱなしというより**間欠的にジョブが起動する**イメージです。

**② 長時間タスクの単発実行**
「今月分30本のリサーチと台本を一気に作る」のようなバッチ処理を投げると、その処理が終わるまで数時間〜半日ほど動き続けることはあります。これは"待機"ではなく"実行中"が長いパターンです。

**③ CI/GitHub Actions連携**
台本や設定ファイルをGitリポジトリで管理し、pushやIssue登録をトリガーにClaude Codeが自動で動く(GitHub Actions経由)構成。イベント駆動なので、これも常時稼働ではなく「トリガーが来たら起動」です。

**④ 監視・自己修復ループ**
自作の投稿パイプラインで「エラーが出たら検知して直す」ような監視スクリプトを常駐させ、そこからClaude Codeを都度呼び出す構成。この"監視側のスクリプト"自体は常時起動になりますが、Claude Code本体はそのたびに短時間だけ呼ばれる形が一般的です。

つまり「Claude Codeプロセスそのものを24時間張り付かせる」というより、**軽量な常駐スケジューラ(cronやGitHub Actions)がトリガーとなり、Claude Codeを都度ヘッドレスモードで起動する**という設計が現実的で、コスト面でも安全です。API従量課金になるため、無制限に走らせるとコストが跳ねる点は要注意です。

## ディレクトリ構成

```
YouTubeChannel/
├── README.md                      # リポジトリ全体の説明、チャンネル一覧
├── shared/                        # 複数チャンネルで使い回すもの
│   ├── voicevox-config/           # 音声合成の共通設定
│   └── scripts/                   # 汎用の自動化スクリプト（共通処理）
│
└── channels/
    └── food-convenience/          # 食（コンビニ・スーパー比較）チャンネル
        ├── docs/
        │   ├── 01-concept.md          # テーマ・型・フォーマットの決定事項
        │   ├── 02-script-templates.md # 台本テンプレ（比較型・〇選型）
        │   └── 03-automation.md       # このチャンネル専用の自動化設計
        ├── characters/                # 立ち絵素材、表情差分パーツ
        ├── assets/                    # 自作イラスト画像素材
        ├── scripts/                   # 台本の完成データ・生成ロジック
        ├── research/                  # 競合リサーチ結果、企画ネタのストック
        └── output/                    # 完成した.ymmpファイル、書き出し情報
```

## 各チャンネルの追加方法

新しいチャンネルを追加する場合は、`channels/` 配下に同じ構成のフォルダを作成してください。

```
channels/
└── <新チャンネル名>/
    ├── docs/
    ├── characters/
    ├── assets/
    ├── scripts/
    ├── research/
    └── output/
```
